# 47. 修 Bug

> 复现、定位、最小修复、回归验证。

所属部分：真实项目工作流

## 你要学会什么

- 用一句话说清《修 Bug》解决的问题。
- 判断什么时候应该使用这个能力，什么时候应该停止等待人工确认。
- 写出一条边界清楚、可执行、可验收的 Codex 提示词。
- 在任务结束后检查 diff、命令结果、截图或日志证据。

## 实战情景

你收到一个可复现问题，需要让 Codex 先判断现象、期望和复现路径，再做最小修复。

## 可复制提示词

```text
请修复这个 Bug。
用户看到的问题：[现象]
期望行为：[正确结果]
复现路径：[页面、按钮、设备、浏览器]
请先复现或说明无法复现，再定位最小原因，做最小修复，并给出回归验证。
```

## 操作步骤

1. 先准备一个无敏感信息的练习项目。
2. 把上面的提示词改成自己的真实任务。
3. 要求 Codex 先只读分析，确认范围后再执行。
4. 修改完成后看 diff，不接受无关重构。
5. 跑项目已有的验证命令；没有命令时，写清楚手动验收方式。
6. 把好用的提示词沉淀到 AGENTS.md、团队文档或自己的速查表。

## 验收清单

- [ ] 任务目标和修改范围写清楚。
- [ ] Codex 没有触碰密钥、账号、生产发布和未授权数据。
- [ ] 交付里有文件清单、验证结果和剩余风险。
- [ ] 如果涉及页面，已经检查移动端和桌面端。
- [ ] 如果涉及 PR，描述里包含问题、改动、验证和风险。

## 常见误区

- 只说“优化一下”，没有目标、范围和验收。
- 看到 Codex 输出很长就以为完成了，没有检查 diff。
- 为了让测试通过而删除断言、跳过测试或隐藏错误。
- 把本地路径、密钥、账号细节写进公开文档或截图。

## 下一步练习

完成这一课后，找一个真实但低风险的小任务，让 Codex 用同样格式输出：分析、方案、修改、验证、复盘。
