# 真实项目工作流

我学 Codex 的方式不是看完教程就结束，而是把它放进真实仓库里跑。真正有效的学习不是“收藏命令”，而是反复完成这些场景：读代码、做功能、修 Bug、补测试、审 PR、验收前端。

## 总原则

1. 先只读，再修改。
2. 先定位文件，再写方案。
3. 每次只做一个目标。
4. 用测试、构建、截图或日志证明结果。
5. 公开内容不写内部来源、私密路径、密钥和不应公开的策略。

## 场景一：读陌生代码库

### 情景

你刚打开一个项目，README 可能过时，目录很多，不能靠猜。

### 提示词

```text
请只读扫描这个仓库，不要修改文件。

请输出：
1. 项目用途
2. 技术栈
3. 入口文件
4. 主要模块
5. 启动命令
6. 测试命令
7. 风险点
8. 下一步适合做的 3 个小任务

如果命令无法确认，请说明依据不足，不要编造。
```

### 讲解

这一步的价值是让 Codex 建立上下文。不要一开始就说“帮我优化项目”，那会导致它打开太多文件、做太多主观判断。

### 验收

- 没有文件被改。
- 命令有来源。
- 风险点包含密钥、部署、生成文件、生产数据。

## 场景二：实现新功能

### 情景

你要给网站加一个“课程情景提示词”模块。

### 提示词

```text
我要新增一个课程模块：情景提示词。

目标：
- 每个教程页至少展示一个真实任务场景
- 每个场景包含：情景、可复制提示词、Codex 应交付、人工验收
- 移动端不能贴边或横向溢出

范围：
- 教程数据
- 教程详情页展示
- 必要的响应式样式

限制：
- 不改部署密钥
- 不改无关页面
- 不公开内部研究对象

请先只读定位文件，给出最小实现方案和验收方法。
等我确认后再修改。
```

### 讲解

这个任务的边界很清楚：模块是什么、字段是什么、移动端怎么验收、哪些不能改。Codex 在这种任务里最稳定。

### 验收

- 页面真的出现情景和提示词。
- 移动端可读。
- 内容没有内部来源。
- 构建通过。

## 场景三：修 Bug

### 情景

手机截图显示教程卡片贴边，图片主体被裁切。

### 提示词

```text
请修复移动端显示问题。

现象：
- 390px 宽度下文本贴边
- 部分图片主体被裁切
- 导航和卡片视觉不统一

期望：
- 页面左右有舒适边距
- 图片主体可见
- 卡片不横向溢出
- 桌面端不被破坏

请先定位相关组件和 CSS，说明根因和最小修复方案。
修改后请检查 390px、768px、1440px。
```

### 讲解

前端 Bug 不要只靠“构建通过”。构建通过只说明代码语法没坏，不说明用户真的能看。

### 验收

- 390px 下没有横向滚动。
- 图片主体没有被切掉。
- CTA 没被底部浏览器工具栏遮挡。
- 桌面布局没有塌。

## 场景四：补测试

### 情景

你修了一个路由问题，希望以后不要再坏。

### 提示词

```text
请为这个行为补测试：

行为：
访问 /、/codex、/tutorial/9-real-workflows.html 都应该渲染学习站页面。

要求：
- 先识别项目现有测试方式
- 不降低现有断言
- 不跳过失败测试
- 如果没有测试框架，请说明，并给出可执行的手动验收脚本

完成后请运行相关检查，并说明覆盖范围。
```

### 讲解

测试不是为了让数字好看，而是把你最怕坏的路径固定住。没有测试框架时，也要让 Codex 写出可执行验收步骤。

## 场景五：代码审查

### 情景

Codex 改完代码，你要在合并或部署前让它自查。

### 提示词

```text
请以代码审查方式检查当前改动。

优先找问题：
1. 用户可见行为是否有回归
2. 移动端是否有溢出、遮挡、图片裁切
3. 是否泄露密钥、内部来源、私密路径或不应公开的策略
4. 是否修改了不相关文件
5. 是否缺少构建、测试、截图或日志证据

输出格式：
- Findings 优先，按严重程度排序
- 每条包含文件和行号
- 如果没有阻塞项，明确说明
- 最后给简短总结
```

### 讲解

让 Codex Review 自己的改动时，一定要让它“先找问题”。否则它容易给你一段看起来很舒服但没什么用的总结。

## 场景六：上线前验收

### 情景

你准备把学习站发到线上。

### 提示词

```text
请做上线前检查，只汇报结果，不执行发布。

检查：
- 构建是否通过
- /、/codex、/founder、/tutorial/9-real-workflows.html 是否可打开
- 390px、768px、1440px 是否有溢出、遮挡、图片失败
- 公开页面是否包含密钥、内部来源、私密路径、不应公开的策略
- 页面 CTA 是否清楚
- 是否有回滚路径

输出：
PASS / WARN / BLOCKED
发现的问题
建议修复
人工确认项
```

### 讲解

上线前检查的重点不是“能不能上传”，而是“用户打开以后是否可靠、公开内容是否安全、失败以后能不能回滚”。

## 一句话

你不是在学一个聊天工具。你是在训练一套可以进入真实项目、能留下证据、能被复盘的工作流。
