# CLI 与终端自动化

Codex CLI 适合喜欢终端、需要远程环境、或者要把任务接入脚本的人。我的建议是：新手先用桌面端理解工作流，再用 CLI 做自动化。

## 安装检查

```bash
codex --version
codex
```

如果命令找不到，先检查 PATH、Node/npm、Homebrew 或公司网络代理。不要一上来就怀疑模型不可用。

## 第一次 CLI 任务

```text
请只读扫描当前项目，列出目录结构、启动命令、测试命令和潜在风险。
不要修改文件。最后给我 3 个适合新手练习的小任务。
```

## 情景课：用 CLI 接手一个远程项目

### 情景

你在服务器或一台新电脑上打开项目，只有终端，没有完整 IDE。你需要先确认项目能不能跑、哪些命令安全、哪些目录不要碰。

### 可复制提示词

```text
请在当前目录用只读方式检查项目。

请输出：
1. 这是一个什么项目
2. 技术栈、包管理器和入口文件
3. 安装、启动、构建、测试命令
4. 哪些命令可能会写入、删除、部署或访问外部服务
5. 哪些文件不应该公开或提交
6. 适合用 codex exec 自动化的 3 个低风险任务

不要修改文件，不要执行部署，不要读取 env 里的具体密钥值。
```

### 讲解

CLI 的优势是快，危险也在这里。你要先让 Codex 建立“命令地图”，再决定是否让它执行。尤其是 `deploy`、`publish`、`migrate`、`sync`、`rm`、`scp`、`rsync --delete` 这一类命令，不要让 Codex 在没有解释和确认的情况下直接跑。

## 常用模式

| 模式 | 用途 | 我的建议 |
| --- | --- | --- |
| 交互模式 | 日常沟通和小步任务 | 适合学习 |
| resume | 回到之前会话 | 适合长任务 |
| fork | 分叉探索方案 | 适合多方案比较 |
| exec | 非交互自动执行 | 适合脚本化，但要有边界 |

## `codex exec` 的使用边界

`codex exec` 很强，但也容易失控。我的规则：

- 只给明确任务，不给模糊目标。
- 明确允许修改的目录。
- 明确必须运行的验证命令。
- 明确什么情况下停止。

示例：

```text
请在当前仓库中只修改 docs/ 目录，补齐 README 的中文学习入口。
不要访问 env、secrets、部署配置。
完成后运行 markdown 链接检查；如果没有检查脚本，就说明无法检查。
```

## 情景课：把文档更新做成一次可控自动化

### 情景

你想让 Codex 批量补文档，但只允许改 `docs/` 和 README，不允许碰源码、部署和密钥。

### 可复制提示词

```text
请用非交互任务完成一次文档更新。

目标：
把 docs/ 中的教程补成更适合新手实操的版本，每篇至少包含：情景、提示词、验收清单。

允许修改：
- README.md
- README.en.md
- docs/

禁止修改：
- src/
- package.json
- 部署脚本
- env、secrets、密钥、账号配置

验证：
- 检查 Markdown 链接是否存在
- 搜索公开文档中是否出现密钥、内部来源、私密路径或不应公开的策略
- 最后输出文件清单、变更摘要、无法验证的项目
```

### 验收清单

- 任务范围没有越界。
- 每篇新增内容都能直接复制使用。
- 没有把内部研究对象写进公开文档。
- 结束时有清楚的 diff 摘要和验证结果。

## 复盘清单

每次 CLI 任务结束后，我会看 4 件事：

1. 改了哪些文件。
2. 为什么这样改。
3. 跑了哪些命令。
4. 哪些风险还需要人工确认。
