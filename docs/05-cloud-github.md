# Cloud、GitHub 与 PR 工作流

Codex Cloud 适合把任务从“聊天窗口”推进到“仓库工作流”。但我不会把它当成无人值守替代品，它更像一个可以异步做事的工程助手。

## 什么任务适合 Cloud

- 根据 Issue 做一个小功能。
- 修复 CI 失败。
- 补 README、文档或测试。
- 做初步代码审查。
- 把重复工程任务做成 PR。

不适合：

- 需要生产密钥的任务。
- 需要访问私密客户数据的任务。
- 没有验收标准的大重构。
- 发布、支付、法律、投资等需要本人确认的动作。

## Issue 到 PR 的提示词

```text
请根据这个 Issue 先只读分析仓库，确认实现位置、风险和测试命令。
如果任务足够明确，再创建一个小范围改动。
PR 描述必须包含：问题、改动、验证、风险、后续建议。
```

## 情景课：把一个 Issue 变成可 Review 的 PR

### 情景

你写了一个 Issue：“移动端卡片文字贴边，图片主体被裁切”。这种任务很适合交给 Codex Cloud 或 GitHub 工作流，因为它有明确现象和验收宽度。

### Issue 模板

```text
标题：修复移动端教程页卡片贴边和图片适配问题

背景：
手机 390px 宽度下，教程页卡片左右边距不足，部分图片主体被裁切。

目标：
- 文本左右有舒适边距
- 图片主体在移动端可见
- 页面不能横向溢出
- 桌面端布局保持现有层级

范围：
- 教程页组件
- 全局响应式样式

验收：
- 390px / 768px / 1440px 截图检查
- 构建通过
- 无公开敏感内容
```

### 交给 Codex 的提示词

```text
请根据这个 Issue 工作。

先只读分析：
1. 可能相关的组件和样式文件
2. 当前移动端布局风险
3. 最小修改方案
4. 需要截图验证的页面

确认任务明确后再修改。

PR 描述必须包含：
- 问题
- 改动
- 390px / 768px / 1440px 验收结果
- 构建结果
- 剩余风险
```

### 讲解

好的 Issue 不是“优化一下移动端”，而是把现象、目标、范围、验收写清楚。Codex 才能稳定产出一个小 PR，而不是做成大改版。

## GitHub 自动化口径

我会把 GitHub 自动化拆成四层：

1. 读 Issue：理解任务，不急着写代码。
2. 改代码：只改和任务相关的文件。
3. 跑验证：测试、构建、lint、截图。
4. 写 PR：把证据和风险讲清楚。

## PR Review 清单

- 这个 PR 是否解决了 Issue？
- 是否修改了不相关文件？
- 是否泄露密钥、路径或内部策略？
- 是否跑过验证？
- 是否说明了未验证项？

Codex 可以帮你写 PR，但最终合并一定要有人看。

## 情景课：让 Codex 审一个 PR

```text
请以代码审查方式检查这个 PR。

请优先找问题：
1. 是否真的解决 Issue
2. 是否有行为回归
3. 是否泄露密钥、内部来源、私密路径或不应公开的策略
4. 是否修改了不相关文件
5. 是否缺少构建、测试或截图验收
6. 移动端是否有溢出、遮挡、图片裁切

输出要求：
- 先列 Findings，按严重程度排序
- 每条包含文件、行号、影响、建议修复
- 如果没有阻塞问题，明确说“未发现阻塞项”
- 最后给简短 summary
```

这个提示词的关键是“先找问题”。PR Review 不是让 Codex 帮你把 PR 夸一遍，而是帮你在合并前发现会伤害用户体验、公开边界或工程质量的问题。
