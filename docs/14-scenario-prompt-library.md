# 场景提示词库

这份文档不是命令大全，而是我自己教 Codex 时最常用的“情景课”。你可以把每个场景当成一次小作业：先复制提示词，再看 Codex 的交付物，最后按验收清单检查。

## 使用方法

1. 先选一个没有生产密钥的小项目。
2. 复制对应场景的提示词。
3. 要求 Codex 先只读分析，再执行修改。
4. 只接受有 diff、有验证、有风险说明的交付。
5. 每次结束后，把好用的提示词沉淀到自己的 `AGENTS.md` 或 Skill。

## 场景 1：接手陌生仓库

### 情景

你第一次打开一个仓库，不知道入口、技术栈、启动命令、测试命令，也不知道哪些目录最危险。

### 目标

让 Codex 先建立项目地图，不改任何文件。

### 可复制提示词

```text
请只读扫描当前仓库，不要修改文件。

请输出：
1. 项目一句话用途
2. 技术栈和主要框架
3. 入口文件、核心目录、配置文件
4. 本地启动命令、构建命令、测试命令
5. 你认为最重要的 5 个文件
6. 可能的风险边界：密钥、部署、生成文件、数据文件
7. 3 个适合新手练习的小任务

最后请告诉我：如果下一步要写 AGENTS.md，你建议写哪些规则。
```

### Codex 应交付

- 项目地图。
- 启动和测试命令。
- 风险边界。
- 小任务建议。
- AGENTS.md 草案方向。

### 人工验收

- 没有文件被修改。
- 命令不是凭空猜的，最好能从 README、package.json、Makefile 或脚本里找到依据。
- 风险边界包含 env、secrets、部署、数据库、账号发布。

### 翻车处理

如果 Codex 一上来就改文件，立刻让它停止，并要求它汇报已经改了什么。重新开始时加一句：“本轮只允许读取文件和运行只读查询命令。”

## 场景 2：实现一个小功能

### 情景

你想让 Codex 做一个真实功能，但不希望它顺手重构全项目。

### 目标

把需求压成小范围 diff，并拿到验证证据。

### 可复制提示词

```text
我要实现一个小功能：

目标：
[写清楚用户能看到什么变化]

范围：
[允许修改的页面、组件或目录]

限制：
- 不做无关重构
- 不修改密钥、部署配置、账号配置
- 保持现有设计风格
- 移动端不能溢出

请先只读定位相关文件，输出最小实现方案、风险点和验证方法。
等我确认后，再开始修改。
```

确认方案后再发：

```text
同意执行。请按刚才的最小方案修改。
完成后请输出：改了哪些文件、为什么改、跑了哪些检查、还有什么风险。
```

### Codex 应交付

- 相关文件定位。
- 最小修改方案。
- 修改后的 diff 摘要。
- 测试、构建或截图证据。

### 人工验收

- 功能真的出现，不只是代码看起来合理。
- 改动没有超出范围。
- 移动端和桌面端都看过。
- 如果没跑测试，要说明原因。

### 翻车处理

如果 Codex 开始大范围重构，让它先暂停，要求列出“必须保留”和“可以撤回”的改动，再只保留完成目标所需的最小部分。

## 场景 3：修复移动端 UI 问题

### 情景

手机上出现文字贴边、图片裁切、按钮挡住、横向滚动或导航过宽。

### 目标

把问题修到真实手机宽度可用，而不是只通过构建。

### 可复制提示词

```text
请修复这个移动端 UI 问题：

现象：
[描述截图里的问题，例如文字贴边、图片被裁切、卡片超出屏幕]

验收宽度：
- 390px 手机
- 768px 平板
- 1440px 桌面

要求：
- 文本左右必须有舒适边距
- 图片不能因为裁切导致主体不可见
- 卡片、按钮、导航不能横向溢出
- 不改变公开页面的核心文案边界

请先定位相关 CSS / 组件，再修改。完成后用浏览器截图或等价方式验收。
```

### Codex 应交付

- 问题根因。
- CSS 或组件修改点。
- 三个宽度的验收结果。
- 如果某张图无法适配，说明原因并给出替代方案。

### 人工验收

- 第一屏能看到品牌、主张和入口。
- 文本不贴边。
- 图片主体可见。
- 页面没有左右滑动。

### 翻车处理

如果图片无论怎么裁切都不好看，就不要硬撑。可以改成 `object-fit: contain`、换图、降低移动端高度，或者在移动端隐藏该媒体模块。

## 场景 4：修 Bug

### 情景

用户反馈一个问题，但你不确定是代码、数据、浏览器缓存还是环境导致。

### 目标

复现问题，定位最小原因，补一个能防止回归的验证。

### 可复制提示词

```text
请帮我修这个 Bug：

用户看到的问题：
[写具体表现]

期望行为：
[写正确结果]

复现路径：
[页面、按钮、输入、设备、浏览器]

请按以下顺序工作：
1. 先只读定位可能相关的文件
2. 给出复现假设
3. 找到最小原因
4. 做最小修复
5. 运行现有测试或补充一个回归验证
6. 解释为什么这个修复不会影响其他流程
```

### Codex 应交付

- 复现路径。
- 根因判断。
- 最小修复。
- 回归验证。
- 剩余风险。

### 人工验收

- Bug 的原路径真的好了。
- 相邻路径没有坏。
- 修复不是简单隐藏错误。
- 没有降低测试断言。

### 翻车处理

如果无法复现，要求 Codex 明确说“未复现”，并列出还需要的信息，不要让它靠猜测乱改。

## 场景 5：补测试

### 情景

功能已经能跑，但你担心之后被改坏。

### 目标

让 Codex 识别测试框架，补一个贴近业务行为的测试。

### 可复制提示词

```text
请为这个行为补测试：

目标行为：
[写清楚输入、操作、预期结果]

要求：
- 先识别项目现有测试框架和测试风格
- 不降低现有断言
- 不跳过失败测试
- 不为了通过测试修改业务逻辑，除非发现真实 Bug
- 测试名称要能读懂业务意图

完成后请运行相关测试，并说明覆盖了什么、没覆盖什么。
```

### Codex 应交付

- 测试文件位置。
- 新增测试说明。
- 测试命令和结果。
- 未覆盖范围。

### 人工验收

- 测试失败时能暴露真实问题。
- 测试不是只检查组件存在。
- 没有跳过、删除或弱化旧测试。

### 翻车处理

如果测试环境复杂，让 Codex 先写最小可运行测试，再单独开一轮处理环境，不要把功能和测试环境问题混在一起。

## 场景 6：PR Review

### 情景

你已经有一个 PR，但不知道有没有隐藏风险。

### 目标

让 Codex 以审查者视角优先找问题，而不是夸改动。

### 可复制提示词

```text
请以代码审查方式检查当前改动。

优先级：
1. 行为回归
2. 安全和密钥风险
3. 权限、发布、账号相关风险
4. 移动端和可访问性问题
5. 缺失测试
6. 文档和命名问题

输出格式：
- 先列问题，按严重程度排序
- 每个问题给出文件和行号
- 如果没有问题，明确说明没有发现阻塞项
- 最后再给简短总结
```

### Codex 应交付

- 按严重程度排序的问题。
- 文件和行号。
- 可操作修复建议。
- 测试缺口。

### 人工验收

- 发现的问题能复现或有明确证据。
- 没有把风格偏好伪装成严重问题。
- 没有泄露内部策略。

### 翻车处理

如果 Codex 只给总结不列问题，提醒它切换到 review 模式：“先 findings，后 summary。”

## 场景 7：Issue 到 PR

### 情景

你想把 GitHub Issue 交给 Codex 做成 PR。

### 目标

把远程任务拆成可审查、可回滚的小 PR。

### 可复制提示词

```text
请根据这个 Issue 工作：

Issue 链接或内容：
[粘贴 Issue]

执行规则：
- 先只读分析仓库和 Issue
- 判断任务是否足够明确
- 如果不明确，先提出问题，不要写代码
- 如果明确，只做小范围改动
- PR 描述必须包含：问题、改动、验证、风险、后续建议
- 不处理密钥、账号发布、生产部署
```

### Codex 应交付

- Issue 理解。
- 实现范围。
- PR 描述。
- 验证结果。
- 未处理项。

### 人工验收

- PR 只解决这个 Issue。
- 没有夹带无关重构。
- 描述里有验证证据。
- 风险边界清楚。

### 翻车处理

如果 Issue 太大，要求 Codex 先拆分成 2-5 个小 Issue，再选择最小的一件做。

## 场景 8：把一次实操变成内容资产

### 情景

你完成了一次 Codex 实操，想把它变成教程、卡片、视频脚本和仓库更新。

### 目标

让一次工作留下长期资产，而不是只停留在聊天记录。

### 可复制提示词

```text
请把这次 Codex 实操整理成内容资产：

输入：
- 任务背景
- 关键步骤
- 关键提示词
- 最终结果
- 验收方式
- 踩坑和修正

请输出：
1. 中文教程大纲
2. 可复制提示词
3. 小红书 6 张卡片标题
4. 60 秒短视频脚本
5. GitHub README 更新建议
6. 人工审核清单

要求：
- 不写内部研究对象
- 不暴露密钥、路径、账号和部署细节
- 文案要像我的公开课程，不要像工具说明书
```

### Codex 应交付

- 教程大纲。
- 卡片标题。
- 视频脚本。
- README 更新建议。
- 风险检查清单。

### 人工验收

- 读者能照着做。
- 没有内部来源和敏感信息。
- 标题有吸引力但不夸张。
- 能自然引导读者找你学习。

### 翻车处理

如果内容像流水账，让 Codex 重写为“问题 -> 操作 -> 结果 -> 复盘 -> 下一步”的结构。

## 场景 9：上线前检查

### 情景

你准备发布网站、文档或教程仓库。

### 目标

上线前做一次安全、质量和移动端检查。

### 可复制提示词

```text
请做上线前检查，只汇报结果，不执行发布。

检查范围：
- 构建是否通过
- 关键路由是否可打开
- 390px、768px、1440px 是否有溢出或遮挡
- 图片、视频、二维码占位是否正常
- 公开页面是否包含密钥、内部来源、私密路径、不应公开的策略
- 页面 CTA 是否清楚
- 是否有回滚路径

请输出：
1. PASS / WARN / BLOCKED
2. 发现的问题
3. 建议修复
4. 可以发布前还需要人工确认什么
```

### Codex 应交付

- 上线状态。
- 问题清单。
- 修复建议。
- 人工确认点。

### 人工验收

- 不只有构建结果，还要有页面结果。
- 没有公开敏感内容。
- 移动端能正常读。
- 回滚路径清楚。

### 翻车处理

如果上线检查发现敏感内容，先停止发布，修复后重新扫描，再构建和验收。

## 我的练习节奏

第一天不要追求“学完 Codex”。你只需要做完三个情景：

1. 接手陌生仓库。
2. 实现一个小功能。
3. 上线前检查。

这三件事跑通后，Codex 就不再是一个聊天工具，而是一个能进入真实项目的工作伙伴。
